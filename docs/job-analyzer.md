# Job Description Analyzer

Overview (`src/app/page.tsx`) includes the full analysis form. Creating an analysis opens `/dashboard/job-match?analysis=<id>` with the saved ID. The extractor uses Playwright for public pages that load their content in JavaScript; it does not use an additional AI or scraping provider. Package manager: npm.

## Flow

1. Paste text, retrieve a public HTTP(S) posting, or import a PDF. URL/PDF extraction does not call AI and does not store the file. Review and correct the extracted text before confirming the analysis.
   LinkedIn links with `/jobs/view/<id>` or `currentJobId` in a search/collection URL are converted to the public `/jobs/view/<id>/` posting. Tracking/search parameters are removed. The importer extracts the selected job description and its company/location, excluding recommendations and sign-in controls. A search without a selected posting is rejected. Public access is required; no LinkedIn session is used.
2. Analyze against the existing confirmed career profile, optionally including an owned structured resume. Results, the original source text, source metadata and evidence are saved in the existing JobOpportunity and JobMatch models. Repeated identical requests reuse persisted results; concurrent requests in one server process share generation. A different profile, resume, language or source invalidates the cache.
3. Inspect requirement categories, priority, verbatim job evidence and profile/resume evidence. Missing evidence is not presented as proof that a skill is absent. Duration, ambiguous and alternative qualifications require verification when they cannot be proved literally.
4. Select a resume for AI adaptation or improvement. Review each proposed change, accept a subset or reject all. Acceptance creates a separate Cv, a ResumeVersion holding its source snapshot, and an association from JobMatch. The original resume is never updated. Continue in the existing resume editor and PDF exporter.
5. Generate a cover-letter or email draft, edit it, then explicitly save or copy. Letters reuse the existing generator prompts/schema and CoverLetter/Conversation entities. Email drafts stay on the owned JobOpportunity. No email is sent. Save the application into JobApplication; its tracker links back to the analysis, resume and letter.

## Matching method

Requirements have explicit source quotations. Titles and matching terms must occur in those quotations; repeated criteria and common technology aliases are deduplicated. Matching searches only professional evidence fields, not contact information, desired roles, billing data or object metadata. It checks complete terms, so Java is not inferred from JavaScript.

Weights are product choices: required = 3, preferred = 1, mentioned = 0.25. Demonstrated criteria receive 1, partial criteria 0.5 and non-demonstrated criteria 0. Criteria requiring verification are excluded from the denominator and reported separately. The score is the weighted mean × 100. It is unavailable for an empty professional profile, fewer than two evaluated criteria, or less than half of all criteria evaluated. Essential skills, desirable skills, experience and qualifications have separate coverage scores. No ATS or hiring-probability claim is made. Old matches without evidence do not contribute a displayed historical score or the analytics average.

The matcher is deliberately conservative and deterministic; it does not infer experience duration, work authorization, proficiency, or semantic equivalence beyond the documented common aliases. Users can confirm missing facts in the central profile and analyze again.

## Integrity, access and limits

- Authentication and owner checks apply to analyses, source/adapted resumes, documents and application relationships. Feature access reuses the existing FREE/PRO/CAREER_PRO matrix, with the existing legacy subscription boolean supported. Generation uses the existing atomic daily AI reservation mechanism; no plans or prices were added.
- Job text: 100–50,000 characters, bounded JSON request bodies. Original and corrected text are separate.
- PDF: actual `%PDF-` signature and MIME validation, 8 MB and 50-page limits, local extraction using the existing `extractPDFText`. Corrupt/empty/scanned documents produce explicit errors. No OCR or additional PDF library was introduced.
- URL: public addresses and standard web ports only; all DNS answers and every redirect are validated. The checked addresses are pinned to the actual HTTP connection, including Node's multi-address lookup mode. Up to four redirects, 12-second request/DNS timeouts, 2.5 MB per resource (including decompressed text), and a 50-second overall extraction deadline. JobPosting JSON-LD is preferred, with cleaned main/article HTML as fallback.
- JavaScript: an unreadable HTML shell with external scripts triggers a fresh headless Chromium session. The reader waits for rendered text to settle. All browser resources use the same validated, DNS-pinned Node transport; direct browser network access fails closed through an unused proxy. Service workers, WebSockets, downloads, popups, embedded documents and write requests are blocked. Each render allows at most 80 requests, 12 MB of text resources and 25 seconds after browser launch; at most two renders run in one server process. The browser closes and pending resource requests are cancelled on completion/error/timeout. No application cookies or logged-in browser profile are used. Login walls and sites that deny public access still return an error.
- AI generation uses a fully required schema, separate from the defaults used to read stored records. Compatible OpenAI models opt into strict Structured Outputs; other callers, legacy models and other providers retain their existing generation modes. Invalid JSON/types or unsupported quotations permit one correction with the same model and the same 45-second deadline. Every result still passes Zod and verbatim-source checks before saving; persistent failures return an error. An operation reserves the user's quota once, including its correction. Provider/authentication failures are not retried by this correction path. Server diagnostics expose validation categories/counts, without generated text, source documents, issue messages, HTTP bodies or credentials.
- Resume changes are restricted to summary, experience descriptions, skill text and project descriptions. A server guard rejects new content words, names, technologies and numbers in each source field. Protected fields (employers, dates, titles, degrees, contact data) cannot be proposed. This intentionally favors conservative rephrasing and reordering. Unsupported suggestions are removed; if none remain, the user continues in the existing editor. Proposals check source signatures and owner access on acceptance, and acceptance claims a proposal atomically.
- Letter/email generation uses factual prompts, rejects unsupported numbers and advertised technical terms not demonstrated by the candidate, and leaves unknown recipients/company addresses empty. User-edited drafts are accepted as explicit user input. These guards are conservative checks, not a claim of automatic semantic fact verification: the interface requires review before saving or copying.

## Schema and deployment

`prisma/migrations/20261017120000_job_description_analyzer/migration.sql` adds source/analysis/document JSON fields to JobOpportunity, evidence/proposal fields, a cache fingerprint and an adapted-Cv relation to JobMatch. Score columns become nullable to represent unavailable scores. It does not delete records or reset the database. Existing records remain accessible; older analyses need to be rerun for evidence-based actions.

Apply pending migrations to the intended database with `npx prisma migrate deploy`, then regenerate the client with `npx prisma generate`. Confirm the target environment before applying migrations to a shared/production database. On Windows, a running development server can lock the Prisma engine DLL; stop that server while regenerating, then restart it.

JavaScript extraction needs a Chromium executable on the server. Local Chrome/Edge is detected on Windows, and common Chrome/Chromium paths are checked on Linux/macOS. On a Linux deployment without a browser, run `npm run setup:job-browser` as the same OS user that runs the app (or set a shared `PLAYWRIGHT_BROWSERS_PATH`). This installs Chromium and its OS dependencies. An existing executable can be selected with `JOB_BROWSER_EXECUTABLE_PATH`; Chromium's sandbox must be supported by the host. Include the browser executable/cache in the deployed environment. Plain HTML extraction remains available without Chromium. Next.js treats Playwright as a server external package.

## Verification

`npm run test:job-analyzer` covers parsing, ambiguity/aliases, deterministic matching, empty profiles, evidence validation, quotas/ownership/cache, SSRF/redirects/DNS pinning, actual valid/corrupt/empty/oversized PDF extraction, resume proposal acceptance/rejection/source preservation, document drafts and application ownership. It uses mocked external AI/network/database calls and the real local PDF library.

`node scripts/verify-job-url.cjs --fixture` runs a real browser against in-memory public page/script/API responses. It checks delayed JavaScript rendering and that private-network and write requests never reach the transport. `node scripts/verify-job-url.cjs https://careers.paoli.io/apply/software-engineer` checks the live public posting, without AI or database access.

`node scripts/verify-job-analysis.cjs --text scripts/fixtures/job-description-pdf.txt` checks live generation with the active configured model on the supplied illustrative PDF text. A public posting URL can be passed instead of `--text <file>`. This calls the provider and can be billable; configuration reads are read-only, no analysis/profile/application is saved, and the user's quota is not modified. Diagnostic output contains only model metadata, validation categories and source-match booleans, never the generated text or API keys. Fixture-based tests cover real SDK handling of malformed field types, a fully required strict schema, a bounded correction, provider compatibility, redacted diagnostics and a single quota reservation/persisted result after recovery.

`node scripts/verify-job-analyzer-ui.cjs` renders the actual React page with compiled project styles and controlled API fixtures in headless Chrome/Edge. It verifies all three imports, review, result evidence, resume review, editable documents, application links, unavailable scores and 12 FR/EN × light/dark × 375/768/1440 layouts. Screenshots and the exact verification scope are in `docs/job-analyzer/`. This is not an end-to-end live database/provider test.

General checks: `npm test`, `npm run typecheck`, `npm run lint`, `npx prisma validate`, `npm run build`. A billable live-provider test is separate from the fixture-based checks; live provider output and arbitrary external job boards are not covered by those fixtures.

After migration, `node scripts/verify-job-analyzer-database.cjs` checks the new columns and adapted-resume relation against the configured database using read-only queries for a nonexistent ID. It does not create accounts or documents and does not print existing records.
